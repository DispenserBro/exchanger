# Дорожная карта проекта Exchanger

## 1. Назначение документа

Этот файл — единая точка отслеживания разработки полноэкранного приложения вендингового аппарата для выдачи жетонов. Он фиксирует текущее состояние, принятые архитектурные решения, порядок реализации, критерии готовности, риски и вопросы, требующие согласования.

Дата формирования первоначального плана: **2026-08-20**.

Последняя актуализация состояния: **2026-09-07**.

## 3. Цель продукта

Создать на Godot 4.7 Mono/C# надёжное портретное киоск-приложение для напольного разменника жетонов. Приложение должно:

1. Показывать интерфейс с единственной встроенной fallback-темой, заменяемой при запуске одним внешним DLC со статическим фоном и отдельными анимированными 2D-спрайтами.
2. Показывать цену жетона, бинарное состояние запаса «много/мало» и бонусные условия.
3. Поддерживать отдельные сценарии оплаты наличными и картой.
4. Безопасно отправлять команду выдачи жетонов через последовательный порт.
5. Дожидаться результата выдачи и показывать успех либо понятную ошибку.
6. Возвращаться в исходное состояние по таймаутам и после завершения сессии.
7. Работать прежде всего на Windows x64 и не связывать UI с конкретной реализацией порта, чтобы в будущем заменить её на Android USB-Serial.
8. Воспроизводить промо-контент на домашнем экране без влияния на основной сценарий.
9. Соответствовать портретному корпусу и пиксельной космической айдентике из подтверждённых референсов.

## 5. Зафиксированные архитектурные решения

### 5.1. Рендерер

Использовать **Mobile renderer (Vulkan)** как базовый режим. Это обязательное требование
runtime-расширения Native Video для MP4/MOV/M4V; оно совместимо с 2D-пиксельным UI и целевой
Windows/Linux конфигурацией. Compatibility нельзя включать, пока требуется Native Video. Для
слабого GPU остаётся `ReducedEffects`; производительность и аппаратное декодирование должны быть
приняты на целевом железе в разделе 4.1.

### 5.2. Слои приложения

```text
Пользовательский интерфейс и экраны
                ↓
Контроллер сессии и конечный автомат операции
                ↓
Сервис протокола контроллера
                ↓
IHardwarePort
       ↙                  ↘
MockHardwarePort     SerialPortHardware
                            ↘
                    UsbSerialHardware (stub)
```

UI не должен знать о `SerialPort`, потоках и формате строк протокола. Он реагирует на типизированные состояния и события контроллера сессии.

### 5.3. Состояния пользовательской сессии

```text
Home
  ├→ CashAccepting
  │    → Dispensing
  │    → Completed
  └→ CardAmountSelection
       → CardCustomAmount (опционально)
       → CardTerminalWait
       → Dispensing
       → Completed
  → Home

Любое активное состояние
  → PaymentDeclined, Error или Cancelled
  → Home
```

Переход в `Completed` разрешён только после подтверждения выдачи контроллером. Сам факт отправки `DISPENSE` не считается успешной выдачей.

### 5.4. Сцены и глобальные сервисы

- Главная сцена: `src/scenes/App/App.tscn`.
- `App` создаёт два `CanvasLayer`: фон с `layer = 0` и UI с `layer = 1`.
- Экраны — отдельные атомарные сцены `Control` со своим C#-скриптом и локальными ресурсами.
- `ThemeManager` и `ScreenManager` регистрируются как Autoload, как требует ТЗ.
- `SessionController`, адаптер протокола и аппаратный сервис принадлежат главной сцене или отдельному композиционному узлу приложения; их не следует без необходимости превращать в глобальные Singleton.
- `ScreenManager` переключает сцены экранов и не содержит бизнес-логику оплаты или выдачи.
- `SessionController` является единственным владельцем состояния текущей операции.
- `HomeScreen` сразу показывает цену, запас, способы оплаты, промо-fallback и контакты поддержки.
- Платёжные сцены разделяются по назначению: `CashPaymentScreen`, `CardAmountScreen`, `CardCustomAmountScreen` и `CardTerminalScreen`.
- `AdvertisementPlayer` является пассивным UI-компонентом домашнего экрана и останавливает декодирование, когда экран скрыт.

### 5.5. Формат темы

В Exchanger существует одна программная fallback-тема. Разрабатываемые темы полностью вынесены в соседний `ExchangerThemeDlcBuilder` и подключаются только как один внешний Godot `.pck`. После загрузки runtime-представление `VendingThemeDefinition` содержит:

- стабильный идентификатор и отображаемое имя темы;
- `Theme` для Control-интерфейса;
- необязательную статическую `Texture2D` фона;
- необязательные `PackedScene` фоновых слоёв/декораций и именованных пассивных визуальных слотов экранов;
- для manifest v2 — полный набор из девяти пассивных визуальных сцен экранов с каноническими
  именами и metadata binding-id;
- fallback-цвет; облегчённый режим хранится в конфигурации приложения.

Сам фон всегда статичен: `ColorRect` с fallback-цветом и, при наличии, неподвижный `TextureRect`. Анимированные спрайты темы добавляются отдельной `PackedScene`; такая сцена может содержать `AnimatedSprite2D` и `AnimationPlayer`, но обязана быть пассивной декорацией и не зависеть от экранов приложения. Фоновые шейдеры, частицы и видео не используются. Промо-ролик допускается только внутри отдельного UI-блока `AdvertisementPlayer` на `HomeScreen`.

Полносценовая тема не содержит бизнес-логику: приложение инстанцирует собственные C#-контроллеры,
до `_Ready` заменяет встроенный визуальный корень сценой DLC и разрешает кнопки, поля и динамические
области через стабильную metadata `exchanger_binding_id`. Вложенность узлов темы свободна. Manifest
v1 сохраняет обратную совместимость как стилевой пакет; v2 требует все девять сцен целиком и
точную копию каталога из 481 обязательного биндинга. Host закрепляет SHA-256 каталога и до
активации отклоняет неверные пути, root-имена, неизвестные или неверно типизированные binding-id
и дубли. Отсутствующий обязательный binding восстанавливается по каноническому `FallbackPath`
узлом старой сцены либо готовым элементом встроенной темы-заглушки.

В основном проекте нет каталога `themes/` и исходных ресурсов тем. Путь к единственному внешнему DLC берётся из пользовательского `appsettings.json`; пакет имеет версионированный manifest, изолированное пространство `res://exchanger_theme_dlc/`, монтируется без замены ресурсов приложения и требует перезапуска для обновления.

### 5.6. Потоки и последовательный порт

- Только реализация `SerialPortHardware` работает с `System.IO.Ports`.
- Чтение выполняется в отдельном потоке с корректной отменой и освобождением ресурсов.
- Фоновый поток не вызывает API Godot и не обращается к Node/Resource/UI.
- Принятые строки и изменения соединения передаются в поток Godot через `ConcurrentQueue` либо `CallDeferred`.
- Разбор строк протокола выполняется отдельно от транспорта и покрывается тестами.
- Повтор команды выдачи после неизвестного результата запрещён без идемпотентного идентификатора операции или явного подтверждения, что первая команда не была принята.

### 5.7. Конфигурация

- Встроенные безопасные значения: `res://config/default_settings.json`.
- Пользовательские настройки: `user://config/appsettings.json`.
- При первом запуске создаётся пользовательский файл на основе значений по умолчанию.
- Ошибочный файл не должен ломать запуск: ошибка логируется, применяются безопасные значения по умолчанию.
- Планируемые параметры: порт, baud rate, таймауты, путь и разрешение внешнего DLC темы, режим имитации оборудования, уровень эффектов, общая громкость и громкость промо-ролика, mute, параметры логирования, цена жетона, карточные суммы, бонусные правила, бинарное mock-состояние запаса, способы оплаты, телефон поддержки и плейлист промо-роликов.
- Секреты платёжного терминала в конфигурации приложения не хранятся; платёжная интеграция находится на стороне внешнего контроллера.

### 5.8. Критические эксплуатационные ограничения

- Godot может включить borderless fullscreen и перехватывать обычные действия приложения, но не может надёжно запретить Alt+Tab, Ctrl+Alt+Del или системные жесты Windows. Полная блокировка обеспечивается Windows Assigned Access/Shell Launcher, политиками ОС и учётной записью киоска.
- Тач-ввод принимает только первое касание (`Index == 0`). Дополнительные касания игнорируются централизованно.
- Минимальная интерактивная область — 64×64 px, основной текст — не меньше 24–32 px на целевом разрешении.
- В интерфейсе нет функций, доступных только по hover.
- Целевой UI проектируется в портретном 9:16 с нативным viewport 720×1280; панели большего разрешения используют масштабирование `canvas_items/expand`.

### 5.9. Требования из визуальных референсов

- Корпус — высокий напольный автомат с зелёной рамой, портретным экраном, физическими приёмниками справа и лотком выдачи ниже экрана.
- Основной стиль — пиксельная космическая тема: тёмно-синий фон, салатовые акценты, белые панели, НЛО и зелёный маскот.
- Домашний экран сразу показывает цену жетона, остаток, выбор наличной/карточной оплаты, действие выдачи, промо-ролик и контакты поддержки.
- Наличная оплата отображает накопленный баланс и инструкции для купюро- и монетоприёмника.
- Карточная оплата содержит пресеты сумм, ввод другой суммы, ожидание терминала и отдельный результат.
- Бонусные жетоны рассчитываются конфигурируемыми правилами, а не зашиваются в UI.
- Референсные файлы не являются production-ассетами; права, финальные исходники, тарифы и бренд требуют подтверждения.

## 8. Сквозные требования к реализации

- Все новые скрипты по возможности пишутся на C#.
- Скрипты Godot Node/Resource объявляются как `partial class`.
- Комментарии в C# ведутся единообразно; для проекта выбран русский язык документации и пояснений сложной логики.
- Экраны не открывают порт, не парсят аппаратные строки и не управляют потоками.
- Ресурсы экранов и компонентов хранятся атомарно в соответствующих папках.
- Пути тем и экранов централизованы в реестрах/конфигурации.
- Сигналы и подписки освобождаются при завершении жизненного цикла узла.
- Таймауты и переходы состояний должны быть детерминированы и тестируемы.
- Новые внешние зависимости и NuGet-пакеты добавляются только при фактической необходимости; разрешение владельца на необходимые NuGet-пакеты получено, назначение и версия каждой зависимости фиксируются в документации.
- После существенных изменений обновляются этот ROADMAP, документация и `agentmemory`.

## 9. Основные риски и меры снижения

| Риск | Последствие | Мера снижения |
| --- | --- | --- |
| Неопределённый протокол контроллера | Переделка транспорта и сценария выдачи | Зафиксировать протокол и реальные примеры обмена до интеграции COM |
| Повтор `DISPENSE` после обрыва | Двойная выдача жетонов | Transaction ID/статус операции; запрет слепого retry |
| Поздний ответ от старой сессии | Выдача не тому сценарию | Идентификатор и поколение сессии, сброс входного контекста |
| UI обращается к Godot из COM-потока | Падения и гонки | Queue/CallDeferred, строгая граница транспорта |
| Слабый GPU | Просадки FPS и задержки тача | Compatibility, лимиты эффектов, fallback-фон, профилирование |
| Ожидание, что Godot заблокирует Alt+Tab | Выход пользователя из киоска | Настройка Windows Assigned Access/Shell Launcher |
| Несовместимый или повреждённый DLC темы | UI не может загрузить внешние ресурсы | Версионированный `.pck`, строгий manifest и программная fallback-тема |
| Неограниченные логи | Заполнение диска | Ротация, лимит размера и срока хранения |
| Android-зависимости проникают в UI | Дорогой порт | `IHardwarePort` и platform-specific composition |
| Неясный результат операции при аварии | Финансовая/операционная ошибка | Журнал транзакций, запрос статуса, безопасный сервисный сценарий |
| Текущий UI остаётся ландшафтным | Несоответствие реальному корпусу | Первым шагом Этапа 2 перейти на 1080×1920 и провести визуальную QA 720×1280 |
| Промо-ролик декодируется всегда | Лишняя нагрузка и просадки FPS | Останавливать плеер вне HomeScreen, ограничить формат/разрешение, иметь постер |
| Референсные цифры приняты за спецификацию | Неверные тарифы и бонусы | Хранить всё в конфигурации и запросить подтверждение владельца |
| Референсные ассеты попали в релиз без прав | Лицензионный риск | `references/` в `.gitignore`; исключить каталог в export preset и использовать только подтверждённые production-исходники |

### 2026-09-07 — Составные действия интерактивного питомца переданы теме

- Добавлен обратно совместимый optional composite contract: тема владеет последовательностью
  клипов и визуальных преобразований, а Exchanger передаёт scoped runtime для проверенного движения
  anchor, политик ввода/границ/опор и посадки на доступную поверхность.
- `space-pixel` реализует `interact`: условный поворот, `come_closer` с scale ×2, повтор `action`,
  вычисляемый проход `falling` через низ/верх экрана без промежуточных опор, `landing` на самой
  высокой опоре и возврат в `idle`; reduced-effects получает сокращённую ветку.
- Runtime автоматически инвалидируется при смене экрана/темы, drag и конфликтующем действии;
  темы без нового API сохраняют прежний одиночный `interact` fallback.
- NUnit и полный `InteractivePetBehaviorSmoke` проверяют выбор верхней опоры, PCK-контракт,
  scale ×2, вертикальный wrap, точный порядок клипов и сохранение прежних drag/drop, маршрутов,
  смены экранов и четырёх циклов празднования.

### 2026-09-08 — Приземление и простой питомца включены в обычное поведение

- После падения при перетаскивании или смене экрана host проигрывает цепочку
  `falling → landing → idle`; `landing` выполняется один полный цикл, а `idle` остаётся состоянием
  ожидания до следующего автономного действия.
- Старые темы без анимации `landing` продолжают сразу переходить в `idle`.
- Запрошенные во время падения четыре цикла `dancing` начинаются только после завершения
  приземления.
- Runtime-smoke с актуальным `space-pixel.pck` и mock-оборудованием подтвердил touch drag,
  смену экранов, `falling → landing → idle`, отложенный танец и composite action. Debug и Release
  прошли по 488/488 NUnit-тестов; 18 аппаратных тестов в каждой конфигурации пропущены.

### 2026-09-08 — Вероятностный простой после ходьбы питомца

- После завершения маршрута host с вероятностью 35% выбирает `idle` на 3–5 секунд, а в остальных
  случаях — `sitting` на 1,5–3,5 секунды. Темы без `sitting` безопасно используют `idle`.
- `InteractivePetBehaviorSmoke` допускает оба корректных результата маршрута и продолжает
  проверять `falling → landing → idle`. Unit-тесты фиксируют границу вероятности.
- Godot 4.7.1 начал штатно добавлять `unique_id` в заголовки узлов `.tscn`; хрупкая проверка
  фиксированного футера Settings адаптирована к дополнительным атрибутам без изменения сцены.
- Debug и Release прошли по 496/496 NUnit-тестов; 18 аппаратных тестов в каждой конфигурации
  пропущены. Runtime-smoke с новым `space-pixel.pck` на mock-оборудовании завершился успешно.

### 2026-09-09 — Действие питомца во время подъёма и спуска

- На каждом ненулевом ребре подъёма или спуска host выбирает случайную точку между 20% и 80%
  пути, останавливает перемещение и выполняет `climbing_action_start → climbing_action →
  climbing_action_stop`; средний клип проигрывается один полный цикл.
- После stop возобновляется исходная анимация направления и продолжается тот же маршрут. Для
  старых тем возможность включается только при наличии всех трёх действий, поэтому частичная
  последовательность не возникает.
- Reduced-effects теперь действительно исключает автономный подъём сразу после landing, но не
  блокирует явно запрошенные маршруты и их climbing-action.
- Debug и Release прошли по 529/529 NUnit-тестов. Полный `InteractivePetBehaviorSmoke` с явным
  актуальным `space-pixel.pck` и mock-оборудованием подтвердил порядок клипов, неподвижность
  anchor во время sequence, продолжение маршрута, смены экранов и составное взаимодействие.
